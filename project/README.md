# Iliya & Pouriya — Portfolio

Bilingual (EN/FA) portfolio for two robotics & embedded systems engineers.
Next.js 16 App Router, Postgres via Prisma, a custom admin panel, self-hosted
on Docker. Built from the specs in `docs/` (see the `docs` branch of this
repo for the full source-of-truth documents this was built against).

## Status

This is a working first pass, generated by Claude from the `docs` branch's
specs, with **placeholder content throughout** (marked `[Placeholder]` /
`[محتوای نمونه]` in the seed data) — swap it for real content via `/admin`
once it's running. See "What's not done yet" below for the honest gaps.

Next.js 16.3 · React 19.2 · TypeScript · Tailwind CSS v4 · Prisma 7.7

## Getting started (local dev)

```bash
npm install
cp .env.example .env      # fill in DATABASE_URL, AUTH_SECRET, etc.
npx prisma generate       # downloads Prisma's schema engine (CLI-side only —
                           # see "Prisma 7" below) — needs normal internet
                           # access; this sandbox's network allowlist didn't
                           # include binaries.prisma.sh, so this exact step
                           # is the one thing that's never actually run
                           # end-to-end. See "Things to verify" below.
docker compose up -d postgres
npm run db:migrate        # creates the schema
npm run db:seed           # seeds the two profiles + placeholder content
npm run dev
```

Visit `http://localhost:3000` for the public site, `/admin/login` for the
admin panel. Seeded admin logins (**change immediately**, see
`prisma/seed.ts`): `iliya@example.com` / `pouriya@example.com`, password
`change-me-now`.

## Prisma 7

Prisma 7 changed its architecture significantly from earlier versions —
worth knowing since it affects a few files here:

- **No connection URL in `schema.prisma` anymore.** It moved to
  **`prisma.config.ts`** (project root), which the CLI (`migrate`,
  `studio`, `generate`) reads instead.
- **`PrismaClient` requires an explicit driver adapter** — the built-in
  connection engine is gone. `lib/db.ts` builds one with
  `@prisma/adapter-pg` (wraps the plain `pg` driver) from the same
  `DATABASE_URL`. `prisma/seed.ts` does the same, since it constructs its
  own client outside the app.
- **The generator is `prisma-client`, not `prisma-client-js`, with a
  required custom `output`** (`generated/prisma`, gitignored, regenerated
  by `postinstall`). This means app code imports Prisma's generated types
  from `@/generated/prisma/client`, not `@prisma/client` — every admin
  component that imports a model type does this.
- One practical upside: driver-adapter queries don't need a runtime query
  engine binary at all (pure TS/JS over `pg`), so the production Docker
  image doesn't need to bundle one. The CLI's *schema engine* (used by
  `generate`/`migrate`, not by the running app) is a separate, still-Rust
  binary downloaded from `binaries.prisma.sh` — that's the one this sandbox
  couldn't reach.
- **Caveat worth knowing**: `prisma` and `dotenv` (which `prisma.config.ts`
  needs) are devDependencies, so they aren't in the pruned
  `.next/standalone` output the production container runs from. Running
  migrations *inside* the deployed container (`docker compose exec app npx
  prisma migrate deploy`, as suggested under Deployment below) will fetch
  those on-demand via `npx`, which needs outbound internet access from that
  container at that moment. If that's not available in your setup, run
  migrations from a machine with the full `devDependencies` installed
  instead (e.g. your local checkout, pointed at the production
  `DATABASE_URL`).

## ⚠️ Things to verify on your machine

This was built in a sandboxed environment whose network allowlist didn't
include `binaries.prisma.sh` or `ui.shadcn.com`, so two things couldn't be
verified end-to-end here and are worth doing first:

1. **`npx prisma generate` / `npm run build`** — confirmed working up to
   the network boundary: `prisma.config.ts` loads, the schema validates,
   and it fails only on fetching the schema-engine binary (403 from this
   sandbox's proxy, not a real error) — see "Prisma 7" above for why that
   binary is CLI-only now. `npm run build` itself has never completed here
   since it depends on `prisma generate` finishing first. `tsc --noEmit`
   was run against everything else and is clean; the only errors it
   reports are "can't find module `@/generated/prisma/client`" (expected —
   that module doesn't exist until `generate` actually runs) and the
   implicit-`any`s that cascade from the same cause. Run `npm run build`
   locally and fix anything that surfaces beyond that.
2. **shadcn/ui components** — `npx shadcn add` couldn't reach the component
   registry from this sandbox, so every component in `components/ui/` was
   **hand-written** to match standard shadcn output (Radix primitives, New
   York style) rather than pulled from the CLI. They should behave
   identically, but if you want to diff against the real thing:
   `npx shadcn diff` once you have registry access.

## Drag-to-reorder

Every ordered list backed by a `sort_order` column is now drag-reorderable
in the admin panel: the projects list (`/admin/projects` — this order is
also the public listing/homepage-featured order), a project's STL models,
and each person's experience timeline. Skills and the two people rows are
deliberately left as-is — skills are grouped by category in the UI rather
than a single flat list, and there are only ever two people, so reordering
wasn't worth the extra complexity in either case.

Implementation is native HTML5 drag-and-drop (`components/admin/use-drag-reorder.ts`)
rather than a library like `dnd-kit` — deliberately, for what are all short
lists (a handful of projects, a handful of models per project). Every
drag handle also has up/down buttons next to it
(`components/admin/drag-handle.tsx`), since native HTML5 DnD doesn't work
on touch devices and isn't keyboard-operable on its own. Reordering updates
local state immediately (optimistic) and persists via a `reorderX` Server
Action per entity (`lib/actions/projects.ts`, `lib/actions/experience.ts`)
that writes the new `sort_order` for every row in one `db.$transaction`.

## Uploads

Every upload surface has a real file-picker flow now, all built on
`lib/uploads.ts` (local-disk, per-category size/extension limits) and a
shared `uploadFile` Server Action (`lib/actions/uploads.ts`):

- **Cover images** (project/post) and **profile photos** —
  `components/admin/image-upload-field.tsx`: single file, URL input doubles
  as a manual-paste fallback, live preview.
- **Project gallery** (multiple images) —
  `components/admin/gallery-upload-field.tsx`: thumbnail grid, multi-select
  file picker, per-image remove. Submitted as a JSON-encoded hidden field,
  parsed server-side in `lib/actions/projects.ts`. Removed/replaced files
  are deleted from disk on save (diffed against the previous gallery) and
  on project deletion, same as the cover image and STL models. Rendered on
  the public project page (`components/site/project-gallery.tsx`) as a
  grid with a click-through lightbox (prev/next, built on the existing
  Dialog component).
- **Resumes** (PDF) — same `ImageUploadField` component, `accept="application/pdf"`,
  preview disabled.
- **STL models** — `components/admin/project-model-manager.tsx`, its own
  flow since it also writes a `ProjectModel` row, not just a URL.

## Content editing

Project and blog post content is **Markdown**, not HTML — edited via a
GitHub-README-style Write/Preview editor
(`components/admin/markdown-editor.tsx`): a formatting toolbar over a plain
textarea, a Preview tab that renders the same way the public site will, and
GitHub Flavored Markdown (tables, task lists, strikethrough, autolinks) via
`remark-gfm`. The public site renders it with `react-markdown`
(`components/site/markdown-content.tsx`), which produces React elements
directly rather than injecting raw HTML — so there's no `dangerouslySetInnerHTML`
anywhere in this flow and no sanitization step needed. `content_en` /
`content_fa` in the database are plain Markdown text.

## Rate limiting

Two endpoints are throttled per-IP (`lib/rate-limit.ts`, `lib/request.ts`):

- **Contact form** (`lib/actions/contact.ts`): 5 submissions / 10 minutes.
  Covers both the Server Action the form actually calls and the `/api/contact`
  fallback route, since both funnel through the same function.
- **Admin login** (`lib/actions/auth.ts`): 5 attempts / 15 minutes, with a
  clear "try again in N minutes" message, reset on a successful sign-in.
  There's also a silent, independently-keyed backstop inside `authorize()`
  in `lib/auth.ts` — same threshold, no custom message — purely to blunt
  someone hitting `/api/auth/callback/credentials` directly instead of
  going through the login page.

**Important limitation**: the limiter is in-memory and per-process, which is
correct for this app's deployment as-is (`docker-compose.yml` runs exactly
one `app` container). If you ever horizontally scale the app service behind
a load balancer, separate processes won't share these counts — swap
`lib/rate-limit.ts` for a shared store (Redis + `@upstash/ratelimit` or
similar) at that point. It also depends on the reverse proxy setting
`X-Forwarded-For` (Caddy does this by default — see the Caddyfile comment);
without a proxy in front (e.g. bare `next dev` in local development),
every visitor falls into the same bucket.

## Deployment

See `docker-compose.yml`, `Dockerfile`, and `Caddyfile`. Update the domain
in `Caddyfile`, set real secrets in `.env`, then:

```bash
docker compose up -d --build
docker compose exec app npx prisma migrate deploy
docker compose exec app npm run db:seed   # first run only — then edit via /admin
```
